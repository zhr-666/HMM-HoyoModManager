# HoYoMod 1.0.0

日期：2026-09-17。状态：已发布。源码标识：发布提交（本次发布一同记录）。

## 变更

### 更新助手静默退出（退出码 0）根因修复

- 现场：用户 0.9.8 → 0.9.9 时窗口提示 `更新助手提前退出（退出码 0，信号 无）`，任务目录只有 `helper-startup.log` 里的两条启动记录，没有 `helper.lock`、`ready`、`status.txt`、`update.log`，说明助手脚本一行都没执行。
- 根因：Node 在 Windows 上把 `detached: true` 实现为 `DETACHED_PROCESS`；该标志让新进程既不继承也不创建控制台。`powershell.exe` 是控制台子系统程序，拿不到控制台就立刻以退出码 0 结束。而 0.9.5 的非 detached 写法虽然能启动，却会在 HoYoMod 退出时一起被结束。**PowerShell 无法同时满足“有控制台”和“脱离父进程存活”。**
- 证据：本仓库 Windows CI 自 0.9.6 起一直失败，报错与用户现场逐字相同；macOS 全程通过。
  - `35057929892`（0.9.5，非 detached，无助手存活用例）：Windows 通过。
  - `35059433070`（新增助手存活用例，仍非 detached）：Windows 失败 `Timed out waiting for survived`。
  - `35059638830`、`35131048375`、`35208561624`（改为 detached）：Windows 失败 `更新助手提前退出（退出码 0，信号 无）`。
  - 外部佐证：[nodejs/node#51018](https://github.com/nodejs/node/issues/51018)（`spawn('pwsh', {detached:true})` 不执行），2026-07-20 结论指出 `DETACHED_PROCESS` 会让 CUI 程序提前终止。

### 更新引擎改为程序自身运行

- 引擎 `src/core/update-run.cjs` 由 `HoYoMod.exe` 以 `ELECTRON_RUN_AS_NODE=1` 运行：GUI 子系统进程不需要控制台，同类问题不会再现。
- 磁盘约定保持不变：`plan.json` 计划、`helper.lock` 单实例锁、`ready` 握手、`status.txt`（`updating` / `complete` / `rolledback`）、`backup` 备份与回滚、完成后启动新版；`--recover-only` 对应原 `-RecoverOnly`。
- 新增启动心跳：应用写 `launch.json`（本次 token），引擎第一件事写 `started.txt`；只有心跳一致才认为引擎在运行，宿主静默退出不再被当成就绪。
- 引擎改用 `original-fs` 处理真实文件：Electron 的 `node:fs` 会把 `resources/app.asar` 当虚拟目录，替换过程必须走物理文件系统。
- 修复“更新成功但新版不启动”：引擎自身处于 Node 模式，重启新版时显式移除 `ELECTRON_RUN_AS_NODE`；否则新版会以 Node 模式启动、没有脚本可跑而立即退出。
- 替换目标已存在时立即报错，不再空等 30 秒重试（Windows 不允许把目录改名到已存在目录上）。
- `HoYoMod-Recover.cmd` 先跑新引擎，失败再回退 PowerShell（用户双击 `.cmd` 时本来就有控制台）。
- 未采用的兜底：`conhost.exe --headless powershell.exe`。CI 运行 `35218547336` 中 conhost 打印完自己的控制台转义序列就以退出码 0 结束，从未运行 PowerShell，因此不保留这条会静默失效的第二引擎；`app-update.ps1` 保持 0.9.9 原样，只服务手动恢复。
- 兼容性：部署方式、替换范围与数据结构不变，仍只替换程序运行文件并保留整个 `data`、启用组合、名称、搭配方案、GIMI 路径、外部程序和自定义背景。更新包格式与 GitHub Release 资产命名不变。

### 构建环境说明

- `pnpm check` 与 `pnpm pack:win` 在本机无法直接执行：pnpm 会先做依赖状态检查并尝试重装，报 `ERR_PNPM_ABORTED_REMOVE_MODULES_DIR_NO_TTY`，且其 store 位于工作区之外不可写。改用等价的 `node scripts/check-syntax.cjs`、`node --test tests/*.test.cjs` 与直接调用 electron-builder。
- electron-builder 打包时需要 pnpm 的 store 目录信息（`node_modules/.modules.yaml` 的 `storeDir` 指向 `~/Library/pnpm/store/v11`，只读），临时指向可写目录后构建通过，构建结束已还原；该文件属于 `node_modules`，不受版本管理。
- 本机 PATH 上的 `node` 垫片运行 `node node_modules/electron-builder/cli.js` 会把脚本路径当成多余参数（yargs 报 `Unknown argument`）；用真实 Node 执行同一命令正常。CI 使用真实 Node。

## 未验证项与已知问题

- 未在用户的 Windows 实机执行一次真实升级：1.0.0 需要先手动覆盖一次程序文件，之后才能用自动更新验证 1.0.0 → 后续版本。
- 界面冒烟脚本未运行（本机没有 Playwright）。
- 更新引擎依赖 `ELECTRON_RUN_AS_NODE`（Electron 默认保险丝配置未关闭它，`package.json` 也没有配置 `electronFuses`）。如果将来有人关闭该保险丝，助手会无法启动；此时会给出明确错误与日志路径，用户仍可按下面的方法手动更新。
- 引擎宿主是程序自身的 `HoYoMod.exe`，因此依赖它旁边的 `icudtl.dat` 等运行时文件（便携版目录本来就有；测试缺失时 Electron 的 Node 模式会以 `0x80000003` 退出并打印 `Invalid file descriptor to ICU data received`）。

## 更新失败时的恢复方法

- 已经遇到更新失败的 0.9.3–0.9.9 需要手动修复一次：退出 HoYoMod，把 1.0.0 完整解压覆盖到原程序目录，保留原 `data`、`GIMI`、`Mods` 及个人文件。不要删除原目录，也不要只替换 EXE。
- 已经开始替换但未完成的更新：关闭 HoYoMod，运行程序目录下的 `HoYoMod-Recover.cmd`（先跑新引擎，失败再回退 PowerShell），并保留 `.hoyo-updates` 中的日志与备份。
- 0.9.9 起，如果程序文件已经手动覆盖成新版，残留的更新记录会在启动时自动收尾，不再要求恢复。
