# HoYoMod 0.9.8

日期：2026-09-17。状态：已发布，Windows 实机验收待补。源码标识：发布提交 `b0de00f`，标签 `v0.9.8`。

说明：0.9.6 与 0.9.7 都是本机草稿，未发布、未交付，改动并入本版本，避免同一个版本号对应两份不同产物。相关过程留在提交历史中。

## 变更

- 修复下载完成后点击“重启并更新”，HoYoMod 关闭后没有替换程序文件、也没有启动新版的问题。
- 原因：助手以 `detached:false` 启动，Windows 上会被并入带 `KILL_ON_JOB_CLOSE` 的 job object，主程序退出时助手被一起结束；`unref()` 只释放事件循环引用，不解除该绑定。
- 助手改为独立进程启动，HoYoMod 退出后继续完成替换并启动新版。日志、隐藏窗口、就绪握手、启动失败诊断与超时清理不变。
- 安装前检查压缩包结构。按 GIMI 目录打包的内容（`mods` 之外的 `ShaderFixes`、`BufferValues`，或 `mods` 之外还有其他文件夹）会直接报错并提示手动安装，不再静默装进受管理目录，导致文件放不到加载位置。单个 `mods` 文件夹或普通模组文件夹的压缩包照常安装。
- “我的模组”的“打开本机库”按钮改为打开程序目录下存放模组副本的 `data/library`，不再与“打开 Mods 文件夹”一样指向 GIMI 的 Mods 目录。动作名从 `openManagedMods` 改为 `openLibrary`，按钮标识从 `open-managed-mods-button` 改为 `open-library-button`。
- 兼容性：部署方式与替换范围均未改变，仍部署到 `GIMI/Mods/HoYoModManaged/<id>`，仍只替换程序运行文件并保留整个 `data`、启用组合、名称、搭配方案、GIMI 路径、外部程序和自定义背景。0.9.5 及更早版本遇到更新助手问题时，仍须手动覆盖一次，旧助手无法通过失败过的自动更新流程修复自身。

## 未验证项与已知问题

- Windows 上助手在 HoYoMod 退出后的实际替换与重启、游戏内模组加载均未验收。
- 两个 Windows 自动化用例（真实 Electron 父进程退出后助手存活、完整 handoff 替换并启动新版）在本机为跳过状态，尚无实际执行证据；需要 Windows CI 或 Windows 实机运行。“修复前该用例确实失败”这一复现结论同样只有 Windows 环境才能取得。
- 本机没有 `playwright` 模块，`scripts/smoke-management.cjs` 与 `scripts/smoke-workshop-navigation.cjs` 中随本次改名更新的按钮与动作断言未实际运行，“打开本机库”的界面行为只经过代码核对与包内源码校验。
- 压缩包结构检查只有单元测试覆盖，未在真实 GameBanana 压缩包与 Windows 实机上验收；拒绝发生在下载并解压之后，下载记录会保留为失败状态以便重试。
- Windows 实机验收未完成即按用户要求发布，助手替换与重启、游戏内加载仍为待验收状态。

## 更新失败时的恢复方法

旧版如果更新助手启动失败，请退出 HoYoMod，将完整 ZIP 解压覆盖到原程序目录，保留原 data、GIMI、Mods 及个人文件，不删除旧目录、不只替换 EXE。已经开始替换但未完成的更新，应先关闭 HoYoMod 并使用原更新目录对应的 `HoYoMod-Recover.cmd` 恢复，同时保留 `.hoyo-updates` 中的日志和备份。
