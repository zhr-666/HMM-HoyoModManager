# 残留更新状态清除与安装结构检查调整

来源：0.9.8 使用反馈（4 项），本记录覆盖其中两项跨模块改动。

## 现场证据

1. 用户按 0.9.8 说明手动解压覆盖更新后，设置中仍持续显示「上次软件更新未完成，请恢复旧版本后重试」，检查更新和下载更新均被拦住。
2. 用户安装的压缩包把 `ShaderFixes` 放在模组文件夹内部（不是顶层），通过了 0.9.8 的顶层结构检查，装进受管理目录后游戏内不生效。

## 原因

### 残留更新状态

手动覆盖只替换 ZIP 内包含的程序文件，不会删除程序目录中的 `.hoyo-updates`。新版启动时 `AppUpdate.init()` 读取遗留的 `current.json` 指向的任务，其 `status.txt` 仍为替换开始前写入的 `updating`，不属于 `complete` / `rolledback`，于是进入 `recovery` 分支并持续提示恢复。实际上程序文件已是新版，替换已经完成，该记录已经过期。

`pending` 分支已具备「目标版本不高于当前版本则判定旧更新未执行」的判断，但替换已开始（`updating`）的记录没有相同的版本核对。

### 安装结构检查

`gimiLayoutFolders()` 只读取解压目录的顶层条目。`ShaderFixes` 位于子文件夹时不匹配任何一条规则，压缩包被当作普通模组安装。而 `ShaderFixes` 需要放在 GIMI 根目录，与受管理的 `GIMI/Mods/HoYoModManaged/<id>` 不同级，放进去不会加载。

## 修复范围

### 残留更新状态

- `init()` 在判定 `recovery` 之前读取该任务的 `plan.json`，取得目标版本。
- 目标版本不高于当前运行版本时，判定替换已经完成：写入 `status.txt` 为 `complete`，删除 `current.json` 指针，删除本程序生成的 `HoYoMod-Recover.cmd`，保留任务目录中的日志、备份和暂存文件供排查。
- 状态回到 `idle`，消息说明更新已完成。
- 无法读取或校验 `plan.json`、目标版本高于当前版本时，维持原有 `recovery` 提示，不做清理。

### 安装结构检查

- 删除 `GIMI_ROOT_FOLDERS` 与「顶层 `mods` 之外还有其他文件夹」两条规则。
- 新增从解压目录开始、大小写不敏感的递归查找：任一深度的文件夹名为 `ShaderFixes` 时拒绝安装，报错提示手动安装到 GIMI 文件夹。
- `BufferValues` 不再拦截；`mods` 之外的其他附带文件夹不再拦截。
- 在线安装与本地导入共用同一校验函数，两者行为一致。

## 边界

- 清理只针对版本号已满足的过期记录；替换中途损坏、版本仍低于目标的记录继续保留恢复入口。
- 自动清理不删除备份，用户仍需自行判断何时回收 `.hoyo-updates` 占用的空间。
- 递归查找只依据文件夹名，不分析文件内容；正常模组自带同名文件夹时同样会被拒绝并提示手动安装。
- 两项改动均需 Windows 实机确认实际效果，macOS 单元测试不能替代。
