# HMM · 原神模组管理

> 界面上显示的程序名是 **HMM**。为了让自动更新、GIMI 里已启用的模组（`Mods\HoYoModManaged`）和更新恢复脚本继续有效，可执行文件 `HoYoMod.exe`、更新包名、更新仓库地址与 GIMI 托管目录名保持 HoYoMod 不变。

Windows x64 便携桌面程序。按分类浏览 GameBanana，下载和安装 Mod，管理本地库及搭配方案，管理 GIMI 的 Mods 目录；启动器首页可打开用户指定的外部 EXE 程序，双击游戏图标进入该游戏的模组工作空间。

开发维护请先阅读 [项目协作规则](AGENTS.md) 和 [开发与发布指南](docs/development.md)。日常基础检查统一运行 `pnpm check`。

## 1.1.2 后台检查更新、界面资源不缓存与启动器细节

检查更新改成后台任务，结果等你主动打开：

- 点「检查更新」（「我的模组」与「设置 → 维护与诊断」两个入口）不再在页面上方冒出全局进度条，也不在检查结束时直接弹出结果窗口。开始时只在右下角弹一条瞬时提示「开始检查更新」（不进历史、不计未读、重启不补弹），检查在后台跑完。
- 检查完成后只做两件事：右下角发一条「检查完成」通知，并在「检查更新」按钮右上角点亮红点。**手动**检查一定有回音（没有更新也报「全部模组已是最新」），**自动/周期**检查保持安静，只有确实查到更新才打扰你。
- 有红点时点「检查更新」直接打开结果窗口，看完红点熄灭；没有红点时点它才发起一次新的后台检查。点那条「检查完成」通知同样打开结果窗口。结果窗口只用缓存的结果渲染，**不会**因为打开而重跑一次网络检查；重启后内存里没有结果时，按模组库里已落盘的检查结果重建，所以历史里那条通知重启后仍然点得开。
- 页面上方的全局进度条整体删除；弹窗内的长任务（替换 Hash 的查找 / 回溯）改在弹窗内就地显示进度，下载进度继续看「下载列表」的每一行。

界面资源不再被缓存，更新后不会再看到旧界面：

- `hoyo://` 下发的每个界面文件都带 `cache-control: no-store`，启动时清掉 `data/session` 下的 Chromium 缓存目录，新增界面文件必须进 `src/core/ui-assets.cjs` 白名单；三者由 `tests/ui-assets.test.cjs` 守住。

启动器与消息中心的界面细节：

- 背景图从侧栏右边线起向右、向上下扩展；侧栏宽度抽成 `--rail-width`，背景左边界与侧栏共用同一个变量，两者永远重合。
- 左栏游戏图标改由游戏数据渲染到 `#game-list`，从栏顶往下按加入顺序排列；进入工作区时图标从当前位置飞向左栏最顶端；横杠移到「全部游戏」正上方并加亮。
- 通知中心去掉铃铛 emoji，改用线性消息 / 警示图标；悬浮窗与面板收小、只留线条。
- 打包前重新生成 `build/icon.ico`；Windows 上显式设置 AppUserModelID，任务栏按 HMM 归组与取图标。

- **术语规则（安装 / 启用）**：**安装**指把下载或本地选择的压缩包解压后的模组副本放进程序目录下的 `data\library`（界面称为「安装库」）；**启用**指把安装库里的模组副本放进 GIMI 文件夹（受管理的是 `GIMI\Mods\HoYoModManaged\<模组 ID>` 或所选 Mods 子目录，界面称为「启用库」）。安装只决定模组在本机库里的分类归属，不写 GIMI；启用才是游戏内生效的一步，且只操作程序自己拥有的部署目录。
- 「我的模组」顶部的两个按钮改名为「安装库」（打开 `data\library`）与「启用库」（打开 GIMI 的 Mods 目录），打开的路径不变。
- 「替换 Hash」从「我的模组」工具条升格为顶栏按钮（与「安装库」「启用库」同一行，只在「我的模组」显示），点开是二级窗口，内含「查找替换 / 替换记录 / 回溯记录」三块：查找替换在窗口内完成预览与执行；替换记录只记录把哪个 hash 换成了哪个 hash、影响了哪些模组；回溯记录列出仍可回溯的批次，逐条「回溯到替换前」，并列出已经回溯过的历史。回溯语义不变（按批次恢复替换前的完整目录，不做反向文本替换）。
- 去掉「我的模组」工具条与「设置 → 维护与诊断」里的「全部停用」按钮；核心的 `disableAll` 动作保留，供自动化与故障排查使用。
- 「新建文件夹」入口去掉，改为随导入完成：点「导入本地模组」（按钮带问号指引，悬浮提示「选择文件后选择安装位置」）→ 选压缩包 → 在 GameBanana 分类里选存放位置。选择规则放宽，**任意一层都可以存放**：停在总分类（大分类）上时库内只建一级目录，模组直接放在大分类文件夹里，不必选到最小子文件夹；没有的文件夹会在确认时自动创建。

## 1.0.1 模组启用改为逐条部署与快捷文件夹

- 修复启用、关闭 Mod 会重建整个 `HoYoModManaged` 的问题。旧实现每次变更都清空并把所有启用中的 Mod 重新复制一遍，因此关闭任意一个 Mod（尤其是关闭全部）会连带删掉 `HoYoModManaged` 下的 `BufferValues`、`Other/Misc`、依赖包和用户手放的文件。现在只针对发生变化的条目操作：列表里每个 Mod 与 `HoYoModManaged/<Mod ID>`（或所选安装文件夹下的 `<Mod ID>`）一一对应，启用时只新增或替换这一个目录，关闭时只移除这一个目录，其余文件夹一律不动。
- 启用 Mod 默认改为创建快捷文件夹：`HoYoModManaged/<Mod ID>` 变成指向本机库副本的真正链接目录（同盘用 Windows 目录联接 junction，免管理员权限；GIMI 与程序不在同一磁盘时自动改用符号链接），不再复制文件，省磁盘、库内改动即时反映到游戏目录。设置中新增「用快捷文件夹启用模组」，关闭后改回复制文件。
- `HoYoModManaged/BufferValues`、`HoYoModManaged/Other/Misc` 这类子目录现在可以作为安装文件夹被选择，模组会以链接形式装进对应子目录。
- 部署事务日志升级为按条目的 v3 格式（暂存目录名 `__hoyo-staging-<uuid>`），失败和断电恢复只回滚受影响的条目；0.9.9 及更早版本的整目录重建日志仍可安全回滚。
- 验证：本机语法检查通过，全部 173 项单元测试通过（Node 24.21.0）。Windows 上 junction 的实际创建、3DMigoto 对链接目录的加载、跨盘符号链接的权限要求仍需 Windows 实机验收；本次未运行界面脚本（本机没有可用的 Playwright）。

## 1.0.0 更新助手改由程序自身运行（修复「更新助手提前退出（退出码 0）」）

- 修复 0.9.3 起一直存在的自动更新失败：点“重启并更新”后 HoYoMod 关闭，既没有替换程序文件，也没有重新启动，窗口提示 `更新助手提前退出（退出码 0，信号 无）`。原因是 Node 在 Windows 上把独立进程实现成 `DETACHED_PROCESS`，被这样启动的 PowerShell 是控制台程序，拿不到控制台就会立刻以退出码 0 结束，脚本一行都没执行（没有 `helper.lock`、`update.log`、`ready`）；改成非独立进程又会在 HoYoMod 退出时一起被结束。本仓库的 Windows CI 自 0.9.6 起一直失败，报错与用户现场逐字相同，macOS 一直通过。
- 更新助手引擎改由程序自身的 `HoYoMod.exe` 以 Node 模式运行：它是 GUI 子系统进程，不需要控制台，因此这类问题不再出现。落盘约定保持不变：`plan.json` 计划、`helper.lock` 单实例锁、`ready` 握手、`status.txt`（`updating` / `complete` / `rolledback`）、`backup` 备份与失败回滚、完成后启动新版；手动恢复脚本 `HoYoMod-Recover.cmd` 同样先走新引擎。
- 新增启动心跳：应用写入本次 `launch.json`，引擎启动的第一件事是写入 `started.txt`。只有心跳对得上才认为助手真的在运行，宿主静默退出不会再被当成就绪；失败时会给出退出码、捕获到的输出和日志路径。
- 修复更新成功后新版不启动的问题：引擎自己处于 Node 模式，重启新版时显式去掉 `ELECTRON_RUN_AS_NODE`，否则新版会以 Node 模式启动、没有脚本可跑，等于更新之后程序再也打不开。
- **已经遇到更新失败的 0.9.3–0.9.9 需要手动修复一次：退出 HoYoMod，把 1.0.0 完整解压覆盖到原程序目录，保留原 data、GIMI、Mods 及个人文件。不要删除原目录，也不要只替换 EXE。** 正在运行的旧版助手无法通过失败过的自动更新流程修复自身。
- 验证：本机语法检查与全部 167 项单元测试；Windows CI（真实 Windows Server 2025）首次全绿，含端到端用例「无控制台 GUI 父进程 → 助手存活 → 替换正在运行的 EXE → 保留 data 与 GIMI → 启动新版」。Windows 上游戏内加载、GIMI 行为仍需实机验收。

## 0.9.8 更新助手重启、安装结构检查与本机库入口

- 修复下载完成后点击“重启并更新”时，HoYoMod 关闭后既没有替换程序文件、也没有启动新版的问题。旧实现把 PowerShell 助手和主程序放在同一进程组，主程序退出时助手会被一起结束；`unref()` 只释放事件循环引用，不能解除这条生命周期绑定。
- 更新助手改为独立进程启动，HoYoMod 退出后继续完成替换并拉起新版；日志写入、隐藏窗口、就绪确认、启动失败诊断和超时清理保持原样。
- 替换范围不变：只替换程序运行文件，保留整个 `data`、启用组合、名称、搭配方案、GIMI 路径、外部程序和自定义背景。
- 安装前检查压缩包结构：按 GIMI 目录打包的内容（`mods` 之外的 `ShaderFixes`、`BufferValues`，或 `mods` 之外还有其他文件夹）会直接报错并提示手动安装，不再静默装进受管理目录，导致文件放错位置、游戏内不生效。只有单个 `mods` 文件夹或普通模组文件夹的压缩包照常安装。
- “我的模组”的“打开本机库”改为打开程序目录下存放模组副本的 `data/library`，不再打开 GIMI 的 Mods 文件夹；查看或手动处理 GIMI 目录仍用“打开 Mods 文件夹”。
- **已经遇到更新失败的 0.9.5 及更早版本仍需手动修复一次：退出 HoYoMod，将 0.9.8 完整解压覆盖到原程序目录，保留原 data、GIMI、Mods 及个人文件。不要删除原目录，也不要只替换 EXE。** 正在运行的旧助手无法通过失败过的自动更新流程修复自身。
- 本版本已通过本机语法检查与单元测试；Windows 上更新助手的实际替换和重启、游戏内效果仍需 Windows 实机验收。

## 使用

1. 完整解压 `HoYoMod-1.1.2-Windows-x64.zip` 到可写文件夹，运行 `HoYoMod.exe`，保留压缩包内的全部文件。0.9.9 及更早版本如果自动更新失败过，需按上面 1.0.0 的说明手动覆盖更新一次。
2. 设置中选择 GIMI 文件夹（含 `d3dx.ini`），程序连接其 `Mods` 子目录，不需要 XXMI 或游戏路径。
3. 从工坊选择模组及压缩包下载，或在“我的模组”导入本地压缩包：先在软件内选择模组副本存放的分类文件夹（大分类也可以直接存放，没有的文件夹会自动创建），再选择 Mods 内的目标文件夹。前置提醒可取消或仍然继续。
4. 在“我的模组”启用、停用、重命名、移除模组；工坊角色模组仅同一角色互斥，不同角色及音效、界面等其他类型可同时启用多个；本地导入模组各自独立。管理器只修改自己拥有的部署子目录。列表上方的「安装库」打开 `data\library`，「启用库」打开 GIMI 的 Mods 目录。
5. 需要打开外部启动器时，先用启动器首页右下角的齿轮选择 EXE，再点击「打开程序」。管理器不传入额外启动参数，不自动启动 GIMI 或游戏。单击左侧游戏图标回到首页；双击图标进入模组工作空间，工作空间顶部同一个图标可返回首页。
6. 在页面空白处右键选择“刷新”更新列表或容量；这不会刷新游戏内的模组。游戏中加载变化请使用外部加载器提供的方式。
7. 窗口右下角是**通知中心**：有未读消息时显示数字角标，新消息先在右下角弹出提示卡（可手动关闭或约 7 秒后自动关闭），关闭后仍保留在历史里。点图标展开历史，可单条删除、全部清除、全部已读；顶部居中的小弹窗只用于刚发起的操作反馈，不会进入历史。

## 批量替换 Hash 与回溯

“我的模组”顶部的“替换 Hash”打开二级窗口，分三块：

- **查找替换**：输入旧值和新值，点击查找预览，确认模组、文件和匹配数量后执行“备份并替换”。扫描所有已安装模组（包括未启用模组）的 `.ini` 及子目录，完整值匹配，不区分大小写。包含注释内的完整匹配；不替换更长标识符中的一部分。接受 8–64 位十六进制值及可选 `0x` 前缀。
- **替换记录**：按时间倒序记录每次替换把哪个 hash 换成了哪个 hash、影响了哪些模组、多少处，以及当前状态（已替换 / 已回溯）。
- **回溯记录**：列出仍可回溯的批次，逐条“回溯到替换前”；已经回溯过的批次连同回溯时间单独列出。

保留原文件编码、BOM 与换行。每批保存受影响模组的完整目录备份，保留在 `data/library`，需要额外磁盘空间，请勿手动清理。已启用模组同步到 GIMI 加载目录。

“回溯到替换前”恢复替换前文件；同一模组的连续替换从最新批次开始回溯。如果模组随后更新、移除、或文件被手动修改，程序会停止回溯，避免覆盖后续内容。回溯保留当前启用状态和搭配方案。文件替换成功不保证新 hash 与当前游戏版本兼容。

## 功能约定

- **安装**：把下载或本地选择的压缩包解压后的模组副本放进程序目录下的 `data\library`（「安装库」）。安装只决定模组在本机库里的分类归属，不写 GIMI。**启用**：把安装库里的模组副本放进 GIMI 文件夹（受管理的是 `GIMI\Mods\HoYoModManaged\<模组 ID>` 或所选 Mods 子目录，「启用库」）。启用才是游戏内生效的一步。
- 预览来自 GameBanana 作者图片，角色名称保留来源站名称。
- **下载后自动启用** 默认关闭；开启后安装成功即切换角色使用的 Mod。
- 工坊支持按下载量、上传时间、更新时间排序；SFW、NSFW 默认均勾选。NSFW 依据来源站分级保守识别，不分析图片；仅勾选 NSFW 时逐页筛选，可能出现空页，可继续翻页。
- 模组工坊和详情中的 NSFW 图片默认模糊，点击可显示；设置中可关闭模糊。我的模组图片始终直接显示。
- 下载记录保存来源网址、所选文件与上传日期。下载使用系统代理设置，显示速度并重试短暂中断；实际速度仍受来源站及网络影响。
- 安装失败会保留下载文件，在左侧“下载列表”查看原因、打开位置或重试。自动启用失败不会丢失已安装的模组。
- “我的模组 → 检查更新”比较文件上传时间，检查完汇总所有更新和失败项。最新上传时间向前 72 小时内的文件全部列出，由用户选择安装。
- **自动检查更新** 默认关闭；开启后启动时与每 6 小时检查，只标记和提示，不自动安装。旧版自动更新设置迁移为自动检查。
- 旧模组缺少文件时间时，尝试按文件编号或唯一同名文件恢复；无法确定时显示“无法判断”，不会将页面编辑误认为文件更新。
- 搭配方案保存所有角色的启用组合，应用空方案会禁用全部 Mod。
- Mod 文件与状态位于程序同级 `data`。搬动整个便携目录后本地库仍可读取；外部 GIMI 和 EXE 路径可能需要重新选择。
- 所有分类均可浏览；自动安装仍面向 GIMI/3DMigoto 格式，其他加载方式的模组请遵循作者说明。压缩包需要包含 `.ini`，不执行 Mod 作者的脚本或程序。DLL、EXE、Python 等程序及脚本随模组原样安装，管理器不会运行它们；链接或不安全路径仍会拒绝安装。下载上限 2 GB，解压上限 4 GB；RAR 解压超过 180 秒会中止，暂不支持加密或分卷 RAR。
- 本管理器仅对工坊中同一角色的角色模组执行互斥（包括该角色的子分类）；本地导入不自动推断人物冲突。作者在**单个压缩包内打包多套互斥版本**时，需要先按作者说明整理为一套再导入，不能仅靠文件夹自动判断所有游戏冲突。

## 代理与下载故障

默认使用系统代理。需要手动指定时，在设置中选择手动代理，填入代理软件实际提供的 HTTP 或 SOCKS5 地址，例如 `http://127.0.0.1:7890`（端口以你的代理软件为准），保存后测试连接。诊断显示 DIRECT 时，流量仍可能被 TUN 接管。

`net::ERR_CONTENT_LENGTH_MISMATCH` 表示传输长度与响应声明不一致，可能涉及服务器、链路中断或代理，单凭报错不能确定原因。程序会保留可续传数据并重试，只有校验通过的完整文件才进入安装。自动重试失败后，可在下载列表重试；实际速度取决于来源站和代理链路。

升级时先退出旧版，完整解压新版，再将旧版整个 `data` 文件夹复制到新版程序旁，保留本地库、设置与替换备份。

需要 Node.js 22+、pnpm，首次安装需要网络。

```sh
pnpm install
pnpm test
pnpm start
pnpm pack:win
```

如果包管理器跳过 Electron 安装脚本，运行 `node node_modules/electron/install.js`。

桌面集成冒烟测试：安装 `playwright` 后运行 `node scripts/smoke-desktop.cjs`，或通过 `PLAYWRIGHT_MODULE` 指定现有 Playwright 包路径。测试使用系统临时目录，不触碰用户 Mod。

## 验证范围

当前开发机为 macOS。自动测试覆盖真实文件部署、同角色互斥、更新回滚、搭配方案、目录搬迁、压缩包校验；桌面测试验证 Electron 界面与主进程连接。GameBanana 接口以真实公开响应验证。

Windows EXE 打开、软件退出后的文件替换/恢复/重启、原生标题栏及具体 Mod 的游戏版本兼容性仍需要 Windows 实机验收。详见 [验收清单](docs/acceptance.md)。
